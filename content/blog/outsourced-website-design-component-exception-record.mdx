# Keep a Component Exception Record for Outsourced Web Design

Shared components make recurring website work easier to review, but not every page should be forced into the same pattern. An exception record keeps a deliberate difference understandable.

## Describe the baseline

Name the component, version, and behavior that normally applies. Include a link to an approved example so the reviewer can compare the exception with the default.

## Explain the user reason

Record the content, accessibility, legal, or task requirement that makes the variation useful. “The stakeholder wanted it” is not enough to preserve a durable exception.

## Limit the scope

State the routes, content types, and states where the exception applies. A narrow boundary makes later reuse safer.

## Assign a review date

Name the owner and the question that should be revisited. An exception may become a useful shared pattern, or it may be retired when the underlying need ends.

## Frequently asked questions

### Should exceptions be forbidden?

No. Useful exceptions are sometimes necessary. The important part is documenting their reason, scope, and owner.

### Who accepts an exception?

The owner of the shared pattern and the owner of the affected content should agree, with accessibility or legal review when relevant.
