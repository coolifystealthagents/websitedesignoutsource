# Design Token Ownership in an Outsourced Website Design Project

Tokens make repeated website decisions easier to maintain, but they also create a boundary question: who may change a shared color, type size, or spacing value?

## Name the owner of meaning

The company owner should approve what a token means, such as an action color or a muted surface. The designer can recommend a value and show its effect across pages. Do not let a one-page request silently redefine a token used by unrelated components.

## Record value and use

The handoff should list the token name, current value, intended use, examples, and any contrast or responsive expectation. Separate semantic names from raw values. A token called action-primary is easier to review than a note that says "use the blue from the homepage."

## Define exception handling

Some pages need a special treatment. Record why the shared token does not fit, where the exception lives, and who reviews it later. An exception should be visible in the component or design file rather than hidden in a one-off override.

## Keep source ownership clear

Return the editable design file, token list, component references, and change record to the company workspace. The outsourced website design team should not be the only place where the system can be inspected or corrected.


## Assign ownership by decision type

The brand owner decides which colors and type styles are on-brand; the design-system owner decides how those values are represented; the page owner approves a route-specific exception. Review a high-traffic page, a content-heavy page, and a conversion page for local values that only look like tokens. Record whether each exception is intentional, temporary, or a candidate for consolidation before extending the system.
