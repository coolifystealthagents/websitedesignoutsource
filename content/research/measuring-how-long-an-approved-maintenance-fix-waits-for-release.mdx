## Research question and scope

How long does an approved maintenance fix wait before it reaches the production site, and which queue conditions make that wait longer? The scope is one outsourced website operation during a defined observation period, not an industry benchmark. The wait matters because a fix that is ready on Monday can lose its value by Friday if a campaign, a support promise, or a security window passes. This protocol measures elapsed time from written approval to a confirmed production release and separates waiting from repair work.

## Population and unit of analysis

Start with a dated list of maintenance fixes approved during the observation window, such as a content correction, a broken form, a style repair, or a small template change. Record the project, the affected route, the approver, the approval timestamp, and the release environment. Keep the original list stable and add later entries with a note. The unit is one approved fix carried by one release. A bundle of fixes shipped together counts as several units for the wait measure but one release event for the deployment record.

## Definitions and measures

Approval starts when the named client owner gives written permission to release, not when the vendor first proposes the change. Release ends when the production route reflects the fix and a second person confirms the result on the live page. Record the queue state at each working day, because a fix can wait for review, for a deployment slot, or for a client content decision. Report the total wait and the largest contributing state separately, so a slow approval and a busy release calendar are not blended into one number.

## Evidence and data dictionary

Each fix needs the approval message, the ticket reference, the release note, and the production URL where the change is visible. Preserve the exact time zone used for timestamps, because an approval sent late on a Friday can look fast when it is converted to another zone. If a fix is returned for more work, record the return separately and restart the release clock only after the revised version is approved. Use project references rather than client names in the analysis file, and keep unpublished changes inside the approved system.

## Test design

Use a census when the number of approved fixes is small enough to trace directly. For a larger set, select a documented sample that includes emergency security fixes, ordinary content repairs, and fixes bundled into a scheduled release. Freeze the sample before analysis so the wait cannot be shortened by choosing only quick wins. Have a second reviewer verify the approval and release timestamps for a subsample, then record disagreements before resolving them. This keeps the measure tied to evidence rather than memory.

## Measures and limitations

The result can support a change to the release calendar, the approval channel, or the queue owner's escalation rule. It cannot prove that a shorter wait produced a better outcome, because a fast release can still miss the original requirement. A long wait is not automatically a vendor failure, since the client may have withheld approval or requested a later window. Report the project mix and the observation window beside the median, and avoid ranking individual coordinators. The useful question is whether the queue shows where an approved fix is stuck.

## Review and next action

Report the median and longest wait by fix type, project, and queue state, and show the share of fixes that waited more than one working day after approval. Separate waits caused by missing approval from waits caused by a release slot or a dependency on another team. Name one change to the queue record, one owner, and one recheck date. For example, a team might add a required [release note](/blog/outsourced-web-design-release-notes-template) and a named deploy window before approval closes. Keep the timestamp sheet with the finding so the next review can repeat the comparison.

## Review cadence

Run the review after each scheduled maintenance release and summarize it at the monthly operations meeting. Repeat it after a change to the deployment calendar, the approver roster, or the support contract. Archive the approval export, the release notes, and the timestamp sheet so the comparison can be repeated. A repeated wait pattern should change the queue rule before the next maintenance window starts. Keep the observation period beside the result so the next review compares like with like.
