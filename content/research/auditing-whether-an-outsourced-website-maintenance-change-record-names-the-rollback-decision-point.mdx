## Research question and scope

A change record usually says that a release can be rolled back if something goes wrong. That sentence is reassuring but incomplete, because it does not say who decides, when the decision is made, or what evidence triggers it. This study asks whether an outsourced website maintenance change record names a rollback decision point, rather than only listing a rollback procedure. The unit of analysis is one change record from a maintenance release, reviewed against the deployment log and the post-release checks.

The scope is the written record produced before and during a production change. It includes the ticket, the release note, the deployment checklist, and any attached rollback plan. The audit does not judge whether the rollback actually worked, because many records describe changes that succeeded and were never reversed. It tests whether the document would let a different engineer make the rollback call without reconstructing the decision from memory.

## Why the rollback decision point belongs in the change record

A rollback plan describes how to return to a previous state, while a decision point describes when that return becomes necessary. The two are often written by different people at different times, and the gap between them appears during the incident. A plan with no decision point pushes the judgment onto whoever is on call, usually under time pressure and incomplete information. The change record is the natural place to fix that gap before the release starts.

The decision point also protects the vendor and the client from a slow, ambiguous argument. If the record says a failed checkout test past a stated threshold requires a rollback, nobody has to debate whether the issue is serious enough. The rule is visible, the evidence is named, and the authority is assigned. That makes the release easier to audit and easier to insure against.

## Defining the rollback decision point

A complete decision point has five parts: a trigger condition, a measurement method, a decision deadline, a named authority, and a communication path. The trigger condition describes the observed state that makes rollback necessary. The measurement method says how that state is detected and recorded. Without both, the trigger is an opinion rather than a test. Each part should be visible in the record itself.

The deadline sets the latest point at which the decision must be made, usually expressed as minutes after release or as a checkpoint in the release sequence. The authority names the role that can decide, and the communication path says who is told and how. A record that names a person rather than a role will fail when that person is on leave, so the audit should treat a named individual as a partial match. The [NIST configuration management guidance](https://csrc.nist.gov/pubs/sp/800/128/final) treats change control as a documented process with defined responsibilities, which supports this structure.

## Building the change-record sample

Start with every production change that touched a shared template, a checkout or form flow, or a third-party integration during the observation window. Those changes carry the highest chance of a rollback decision, which makes the sample more informative than a random draw. Include at least one low-risk content release as a comparison, because a record should scale its detail to the risk. Keep the original ticket and the deployment log for each case.

Record the release date, the change type, the number of routes affected, and whether the release happened during or outside business hours. Note whether the record was written before the release or reconstructed afterward. These fields explain differences in quality without turning the audit into a blame exercise. They also show whether thin records cluster around a particular type of work.

## Coding the pre-change state and success criteria

Before a rollback can be judged, the record needs a baseline. Check whether it names the version, commit, or backup that represents the state to return to. A record that says "restore the previous version" without identifying that version leaves the next engineer to guess. Mark the baseline as present only when the identifier is specific enough to retrieve. Otherwise the restore target is a rumour.

Success criteria are the other half of the baseline. The record should say which pages, flows, and integrations must work after the release, and what counts as working. A checkout test that stops before payment confirmation is not a complete success check. Code each criterion as present, vague, or absent, and keep the wording so a second reviewer can check the judgment.

## Checking trigger conditions and thresholds

Triggers should be observable events, not feelings. A usable trigger names a symptom, a scope, and a threshold, such as a payment failure on more than one attempt in ten during the first hour. A record that says "roll back if issues occur" has no threshold and no scope. Mark it as a placeholder rather than a decision rule, even when the rest of the plan is detailed.

Check whether the threshold matches the risk of the change. A minor spacing release may not need an automatic rollback rule, while a change to tax calculation probably does. The audit should record the change type beside the trigger so the report can show whether high-risk releases receive stronger rules. A uniform rule applied to every change is a sign that nobody thought about risk.

## Checking decision authority and communication

The authority section should name a role, a backup role, and the time window in which each can act. A record that lists the account manager as the decider, without saying who covers evenings, is incomplete for a release that runs after hours. Check whether the authority can actually stop the release, because a coordinator without deployment access may only be able to ask. The record should also say how the decision reaches the person who executes the rollback.

Communication is part of the decision, not an afterthought. The record should name who informs the client, who updates the status page, and what message is used while the rollback runs. A decision made silently and communicated an hour later still leaves users and support staff in the dark. Mark the communication path as present only when it names a channel and a responsible role.

## Checking the post-decision verification

The record should say how the team confirms that the rollback restored service. That check is different from the release check, because the target state is the old version rather than the new one. Look for a short list of pages, flows, and logs to inspect after the rollback, with a named owner for each. A record that ends at "rollback executed" leaves the actual recovery unverified.

Also check whether the record captures the evidence that justified the decision. Screenshots, error logs, alert timestamps, and test results should be attached or referenced. Without that evidence, a later review cannot tell whether the rollback was necessary or whether the team reacted to a false alarm. The audit can count how many decisions have supporting evidence and how many rely on a narrative written afterward.

## Distinguishing a rollback plan from a rollback decision

A rollback plan is a set of steps, and it can be copied from one release to the next with minor edits. A decision point is specific to the change, because the trigger and the risk depend on what is being released. A record that reuses the same plan text across every change is not necessarily wrong, but it should not be counted as a decision point. The audit separates the two so a thick appendix does not inflate the score.

The distinction matters when a vendor claims maturity. Many proposals show a rollback plan as proof of safety, yet the plan may never have been paired with a trigger. Ask for one recent record where the decision point was written before the release and one where a rollback was actually considered. The pair reveals more than a template library. A template library is not evidence of a decision habit.

## What the record cannot prove

A change record is a plan and a log, not a guarantee. It cannot prove that the named authority was available, that the trigger was measured correctly, or that the rollback completed within the stated time. It also cannot show whether the team would make the same decision under real pressure. Treat the record as evidence of preparation, not as evidence of performance.

The audit also cannot compare vendors fairly without context. A single-maintainer site will produce a shorter record than an agency with a release team, and that difference may be appropriate. Report the project size, the change type, and the release window beside the findings. The purpose is to improve the next release record, not to rank vendors on document length.

## Limitations and threats to validity

The sample comes from one relationship and one observation period, so the findings describe that history rather than the vendor's general practice. A quiet period with few risky releases can make the records look better than they are. Access to deployment logs and alert history may be limited, which weakens the check on whether the stated trigger was measured. State those limits in the report.

Two reviewers should code a small overlap sample before the full pass. Disagreements usually reveal that one reviewer counted a rollback plan as a decision point or treated a vague threshold as present. Resolve the rule with the definitions above, recode the sample, and keep the change log. A transparent method matters more than a large sample with inconsistent judgment.

## Reporting and next action

Report one row per change with the release date, change type, baseline, success criteria, trigger, threshold, authority, deadline, communication path, and evidence status. Add a short note on whether the rollback decision point was written before the release. Summarize the share of records with a complete trigger and the share with a named backup authority. Keep the quoted wording in an appendix so the summary can be checked.

Agree one change with the vendor and a date to recheck it. A useful first step is a release template with a trigger, a threshold, a decision deadline, a deciding role, a backup role, and a post-rollback check. The [NIST patch management planning guide](https://csrc.nist.gov/pubs/sp/800/40/r4/final) and the [NIST Security and Privacy Controls catalog](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) provide public references for change control and contingency planning. Review the next three releases against the template before changing the contract.
