## Research question and scope

This audit asks whether a website launch checklist includes a step that verifies analytics and consent settings on the live site. The unit of analysis is the checklist item and the evidence attached to it, not the tag configuration alone. A qualifying item names who performs the check, when it happens relative to launch, which tags and consent categories are covered, and what result counts as a pass. The review covers launches that introduced a new tag manager container, a new consent banner, or a material change to either.

The scope includes analytics tags, advertising or remarketing tags, the consent management platform, and the cookie or preference panel that visitors see. It excludes purely internal dashboards that no visitor tag writes to. The audit does not certify legal compliance, because that judgement belongs to counsel. It tests whether the launch process asked for evidence that tags behave correctly and that consent choices are respected before and after the visitor decides.

## Why analytics and consent checks slip through

Analytics and consent are easy to omit because they sit between several owners. The design vendor may place the container, the client's marketing team may own the tag configuration, and a separate provider may run the consent banner. Each party can reasonably assume another one verified the result. The launch checklist then covers what the build team can see, such as pages, forms, and redirects, and leaves the invisible layer untested.

The timing makes the gap worse. Consent behaviour can only be confirmed on the live host, after the banner loads and the visitor makes a choice. A checklist written for the cutover moment may include "deploy the tag container" and stop there. That item confirms the snippet exists, not that it waits for consent or that events arrive in the analytics property. The distinction is the centre of this audit.

## Defining the checklist item

A checklist item is more than a single line about analytics. It should name the tag manager container, the analytics property, the consent categories, and the test method. It should state the expected behaviour before consent, after acceptance, and after rejection. It should also name the person who signs off and the place where the evidence is stored.

The item should describe the failure path as well. If a tag fires before consent, who disables it and how quickly? If an event is missing, who owns the fix and how is it rechecked? Write the expected result next to the step so a reviewer can mark it pass or fail. A vague item produces a vague result that cannot be audited later. The audit scores the presence of these details, not the confidence of the person who wrote the line.

## Sampling checklist versions

Collect the launch checklist versions that were actually used, including spreadsheets, ticket templates, and project boards. Note the version date and the owner, because a later revision may look better than the one used on launch day. Search for terms such as analytics, tag manager, consent, cookie, GDPR, tracking, and pixel. Record every item that touches those terms, even when it appears inside a general quality section.

Then sample the tag and consent inventory. If the inventory is short, review every entry; if it is long, stratify by vendor, purpose, and consent category. Include the analytics base tag, at least one conversion event, and any advertising tag that depends on consent. Keep the selection rule in the audit file so a second reviewer can reproduce the sample. Gaps in the inventory are findings in their own right.

## Testing tag firing before consent

Open the live site in a clean browser profile with no stored consent choice. Watch the network requests and the tag manager preview before interacting with the banner. Record every request to an analytics or advertising domain, and note whether it carries identifiers. A tag that fires at page load, before any choice, is a finding even if the banner appears a moment later.

Repeat the test with the banner blocked by script settings to see what loads when the consent tool fails. A consent implementation that defaults to tracking when its own script does not load is a common and serious gap. Record the observed behaviour rather than the intended design. The audit should distinguish a tag that loads but sends no data from one that sends identifiers immediately.

## Testing consent state after a choice

Accept all categories and confirm that the expected tags fire and that events appear in the analytics debug view. Then clear storage, reject optional categories, and repeat the check. Record whether any non-essential request still occurs after rejection, including pixel loads and server-side calls that the browser cannot see directly. The rejection path is the one most often left untested.

Test a partial choice as well, because many banners allow analytics but not advertising. Confirm that the tags tied to each category follow the choice independently. Then change the choice from accept to reject and check whether previously loaded tags stop or are removed. A consent system that only reads the choice at page load can leave a tag running until the next navigation.

## Verifying analytics data and identifiers

Configuration checks should confirm the property identifier, the measurement protocol version, and the event names that the site is expected to send. Record a small set of events, such as page view, form submit, and outbound click, and confirm they arrive with the expected parameters. Capture the debug output as evidence rather than describing the result from memory. A tag that fires but reports to the wrong property looks healthy in the browser and empty in the report.

Check whether identifiers are truncated, hashed, or sent in full where the design says otherwise. Confirm that test traffic is filtered so the audit does not pollute production reports. Note the time zone and currency settings if the site records conversions, because a mismatch distorts later analysis. These checks are quick when the expected values are written down before launch.

## Checking the consent record and withdrawal

A consent platform should leave a record that a choice was made and should make withdrawal as easy as acceptance. Verify that the preference link or button is reachable after the banner is dismissed. Confirm that withdrawal takes effect without requiring a support ticket. Record where the consent state is stored and how long it persists.

The audit should also check the banner text against the categories it actually controls. A banner that lists three purposes while the platform exposes five creates a consent record that does not match what the visitor saw. Compare the visible categories line by line with the platform's category names. That mismatch matters more than the visual polish of the banner, because it undermines the evidence that the choice was informed.

## Scoring checklist inclusion and evidence

Use a three-level score for the checklist item. Complete means the item names the owner, the timing, the tags and categories covered, the expected behaviour before and after a choice, and the failure path. Partial means the item exists but misses one or more of those elements. Absent means no item addresses analytics and consent verification.

Score the evidence separately. Verified means a dated record covers the sampled tags and matches the intended consent behaviour. Partial means the record exists but covers a subset or lacks the observed requests. Missing means no record was produced. Keeping the two scores apart matters, because a good checklist with no evidence and a weak checklist with strong evidence call for different fixes.

## Common failure patterns

The most common pattern is a banner that blocks the visual cookie notice but not the tag itself. The page looks compliant while requests leave before consent. A second pattern is a tag added after launch through the tag manager and never recorded in the inventory, so the checklist and the live container drift apart. Both look like passes in a simple visual check.

A third pattern is a test performed only in the accept state, which never exercises rejection or withdrawal. A fourth is a consent record stored on one subdomain while the site runs on several, so a choice made on the main site does not carry to checkout. The audit should count these patterns rather than treating each as a one-off. Recurring patterns point to a missing step in the launch template.

## Limitations and threats to validity

This audit reviews checklists, records, and a sample of live behaviour. A team may have verified everything thoroughly without writing it down, and a tidy record may describe a rushed test. The reviewer should corroborate the evidence with tag manager version history, analytics debug output, and the consent platform's own logs. The report should state which sources were available and which were not.

Live tags also change after launch, so a test run weeks later measures the current state rather than launch day. The audit should date every observation and avoid presenting a later result as proof of launch behaviour. Legal compliance is outside the method entirely, because a technically correct consent flow can still fail a legal test. The report should say what the sample can and cannot support.

## Reporting and next action

Report one row per checklist version and one row per sampled tag or event. Include the checklist item, the consent category, the expected behaviour, the observed request or event, and the evidence reference. Mark each row complete, partial, or missing, and attach the date of the live test. Summarize failures by pattern so the launch owner can fix the template rather than only the individual tags.

The [Google Analytics consent mode guide](https://support.google.com/analytics/answer/9976101) describes how tag behaviour can change with consent state. The [ICO guidance on cookies and similar technologies](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guide-to-pecr/cookies-and-similar-technologies/) explains the consent standard that a banner is meant to meet. The [European Commission data protection page](https://commission.europa.eu/law/law-topic/data-protection_en) sets out the wider legal frame. These references inform the method; they do not report a result for any launch in this sample.
