# Testing Website Downloads From Link Label to Saved File

**Published: September 9, 2026**

A download crosses page copy, HTML behavior, an HTTP response, browser policy, and a file stored outside the website. This research note defines evidence at each boundary. Sources were reviewed September 9, 2026.

## Research question

How can an outsourced delivery team verify that a download is understandable before activation and recognizable after it is saved?

## Methodology and scope

We compared HTML and HTTP standards, IANA media registrations, WCAG link guidance, PDF accessibility material, and browser references. Scope includes first-party public downloads initiated from links. Authenticated exports and malware analysis are outside scope.

## Evidence synthesis

HTML provides a download attribute, but browsers may apply origin and security constraints. HTTP Content-Disposition can suggest inline or attachment handling and a filename. Content-Type describes the representation. None of those fields alone proves that the bytes match the advertised file or that a person understands the link.

Accessible link purpose is evaluated from its text and context. File type, size, language, and date may matter when they affect the choice. The saved filename becomes an important identifier after surrounding page content disappears.

## Practical interpretation

Inference: record visible label, accessible name, source URL, status, redirects, media type, disposition, byte size, final filename, and a safe open result. Compare advertised and actual facts. Retest after replacement and include stale-link monitoring for high-value documents.

## Inference limits and limitations

Browser download prompts and filename sanitation differ across platforms. Response inspection does not establish document accessibility, safety, accuracy, or legal approval. Those require their own reviews and owners.
