# Evidence Packs for Outsourced Website QA

An evidence pack turns a QA opinion into a reviewable record. It should show what was tested, under which conditions, what failed, what changed, and who accepted the result.

## Key Stats

- WCAG 2.2 has 4 principles (W3C)
- HTTP defines 5 status code classes (IETF)
- Git records changes as commits with parents and metadata (Git)

## Key Takeaways

- Make test conditions part of the evidence, not a footnote.
- Separate defect, reproduction, expected result, and retest.
- Keep approval and exception decisions with the company.

## Methodology

This synthesis uses WCAG, HTTP semantics, Git documentation, and W3C testing guidance. The evidence model adapts these references to outsourced website review and does not supersede domain-specific testing standards.

## Pack contents

Include build identifier, route list, browser and viewport, test data class, screenshots or recordings, console or network notes where relevant, issue IDs, retest output, and approval state. Keep sensitive data out of captures.

## Release decision

Summarize open findings by severity and owner. A release decision should state what is fixed, deferred, accepted, or blocked. The vendor can recommend; the company should authorize risk acceptance.

## Consolidated statistics

The cited references use 4 WCAG principles, 5 HTTP status classes, and Git commit metadata. These facts describe the evidence vocabulary and do not establish release quality by themselves.

## Frequently asked questions

### Are screenshots enough?

No. They help with visual state, while reproducibility also requires route, build, test conditions, steps, and expected behavior.

### How long should evidence be retained?

Use the company's release and retention policy, and avoid retaining personal or secret data in test artifacts.
