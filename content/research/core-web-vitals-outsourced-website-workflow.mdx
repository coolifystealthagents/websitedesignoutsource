# A Core Web Vitals Workflow for Outsourced Website Work

Performance work benefits from a shared measurement contract. The client defines the page types and user journeys; the production team records field and lab evidence; the approver decides whether a change is ready.

## What to measure

Google’s current Core Web Vitals are Largest Contentful Paint, Interaction to Next Paint, and Cumulative Layout Shift. Use field data for real-user experience and lab data for diagnosis. Do not treat a single synthetic run as a population result.

## Handoff controls

Record the URL, device assumptions, test date, build identifier, finding, suspected cause, change, and retest. Keep image optimization, script loading, font behavior, layout stability, and third-party code as separate work items so ownership stays clear.

## Methodology

This note compares official web performance definitions and measurement tools. Thresholds and tool behavior can change, so the linked documentation is the source of truth at review time.

## Key Stats

- Core Web Vitals currently cover LCP, INP, and CLS (web.dev)
- Chrome UX Report data is based on real user experiences (Chrome)

## Key Takeaways

- Pair field evidence with lab diagnostics.
- Measure representative templates, not only the home page.
- Recheck after content, dependency, and layout changes.

## Frequently asked questions

### Is a good Lighthouse score enough?

No. It is lab evidence under an assumed environment, not a guarantee about field users.

### Who should own regression review?

The delivery team should run the test; the designated site owner should approve the result.
