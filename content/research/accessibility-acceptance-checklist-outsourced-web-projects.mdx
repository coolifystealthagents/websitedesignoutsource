# Accessibility Acceptance Checklists for Outsourced Web Projects

An outsourced web project is easier to review when accessibility is treated as acceptance criteria rather than a final opinion. This research note turns established guidance into a repeatable handoff.

## What the evidence supports

WCAG 2.2 organizes accessibility around four principles: perceivable, operable, understandable, and robust. A practical checklist should map each page and component to those principles, then record the test result and owner.

## A workable review sequence

Start with keyboard-only navigation, visible focus, headings, labels, alternative text, contrast, error messages, and responsive zoom. Then run automated checks as a supplement. Automation finds some defects, but it does not substitute for human review of meaning, order, or task completion.

## Methodology

This is a synthesis of standards and testing guidance published by standards bodies and platform maintainers. It makes no claim that a checklist alone proves legal compliance.

## Key Stats

- WCAG 2.2 has three conformance levels: A, AA, and AAA (W3C)
- WCAG 2.2 contains 13 guidelines grouped under four principles (W3C)

## Key Takeaways

- Put testable accessibility criteria in the brief before production starts.
- Keep automated findings and human findings in the same acceptance record.
- Escalate unresolved barriers with a named owner and retest date.

## Frequently asked questions

### Does an automated scan prove accessibility?

No. It is useful for repeatable checks, but keyboard, screen-reader, content, and task testing still matter.

### When should the checklist be used?

At brief approval, component review, page QA, and final handoff.
