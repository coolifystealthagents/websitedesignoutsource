# Evidence for Focus-Trap Reviews in Outsourced Website Design

## Research question

What should a design review prove about keyboard focus when a website opens a modal, drawer, or other temporary interface?

## Evidence scope and method

This research uses WAI-ARIA Authoring Practices, WCAG keyboard guidance, HTML semantics, and interaction-design evidence. It evaluates the opening, use, and closing sequence as one focus path.

## Focus is part of the interaction

A drawer can look correct and still strand a keyboard user behind it. A modal can close visually while leaving focus on an element that no longer exists. These failures are easy to miss when an outsourced website review relies on a mouse and a screenshot. The unit of review should be the sequence: what opened the temporary interface, where focus moved, what controls were reachable, how the interface closed, and where focus returned.

## Name the temporary boundary

The design brief should say whether the interface is modal, non-modal, a navigation drawer, or a disclosure. That choice affects whether background content remains available and how focus should behave. The role and accessible name should match the visible purpose. A component that is called a modal in a design file but behaves like an ordinary panel creates ambiguity for both implementation and review.

## Test entry and containment

Start with keyboard focus on the trigger. Open the interface without a pointer, identify the first useful control, tab through the available controls, and confirm whether focus escapes when it should not. Test the close button and the Escape key where the pattern calls for it. Inspect the accessible name, visible focus indicator, reading order, and the background content at increased zoom.

## Test return and interruption

After closing, focus should return to a sensible element unless the triggering context no longer exists. Test what happens when validation fails, when the route changes, when a network response is delayed, and when a user opens the interface on a narrow viewport. These states matter because production implementations often add behavior that was not present in the original design concept.

## Document the evidence

A useful record names the trigger, interface type, browser, keyboard sequence, expected focus target, observed focus target, and the route. A short recording may help a remote design pod understand the sequence, but it should not replace a text finding that can be retested. Separate a missing visual focus style from a broken focus boundary because the fixes and risks differ.

## Limits

A keyboard review can establish behavior for the tested pattern and conditions. It cannot prove compatibility with every assistive technology or every custom component state. It also cannot decide whether the interruption belongs in the product at all. That is a task and content decision for the owner, informed by the evidence.

## Conclusion

For outsourced website design work, a focus review can show whether a temporary interface manages keyboard movement and return conditions as intended. It cannot establish overall accessibility from that interaction alone. The owner and production team should preserve the tested route, conditions, source basis, and unresolved assumptions so the next decision can be made from the same record.

## Frequently asked questions

### Does this research guarantee a successful website outcome?

No. It describes a bounded review method and the evidence it can support. The result depends on the tested route, content, users, implementation, and decisions made by the site owner.

### Who should approve the final decision?

The owner of the affected service, content, or user task should approve the decision. The outsourced website team should provide the evidence and state what remains outside the review scope.
