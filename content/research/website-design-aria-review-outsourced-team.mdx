# ARIA Review Boundaries for Outsourced Website Design

ARIA can describe custom interface behavior, but it cannot substitute for an understandable interaction model. A design review should first ask whether native HTML expresses the component, then verify any remaining roles, states, and properties against the implemented behavior.

## Research basis

The WAI-ARIA specification and Authoring Practices define roles and interaction patterns, while the HTML specification supplies native elements. WCAG's name, role, value and keyboard criteria make the handoff testable across visual and assistive interfaces.

## Review method

For each custom component, record its purpose, keyboard model, focus behavior, accessible name, state changes, and the native element considered. Test the component in its collapsed, expanded, disabled, selected, loading, and error states where those states exist.

## Frequently asked questions

### Should every component use ARIA?

No. Native HTML is usually the better starting point when it expresses the required behavior.

### Can a screenshot prove an ARIA implementation?

No. The review needs rendered semantics and interaction tests in addition to visual evidence.
